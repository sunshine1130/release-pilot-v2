# 技术文档 · 关联算法规格

> 配套：[技术方案-飞书需求同步与GitLab分支直读.md](./技术方案-飞书需求同步与GitLab分支直读.md)
> 本文是**唯一算法真相**：L1/L2/L3 的精确行为、边界、夹具与反例。实现与测试都以本文为准。

---

## 1. 术语

| 术语 | 定义 |
|---|---|
| 发布主线 | 分支合并的最终归宿，默认 `origin/master`，可配置 |
| 基线 `mb` | `git merge-base <主线> <分支>`，即该分支与主线的分叉点 |
| **独占提交** | `<mb>..<分支>` 区间内、**沿 `--first-parent` 链**可达的提交 |
| 需求ID | 10 位数字串（如 `7000000012`）；**不硬编码长度**，用「连续数字且左右非数字」判定 |
| 已合并 | 独占提交数为 0（该分支的改动已全部进入主线） |
| 未登记分支 | 独占提交 > 0，但三条路径都关联不到任何需求ID |

## 2. L1：独占提交反查

### 2.1 精确命令序列

> **v2 实现已简化为「每分支一次 git」**，与下面的等价写法相比省掉 merge-base 与 rev-list 两次进程调用（28 分支 85 次 → 29 次，实测 6.4s → 2.9s）。等价性已实测：提交集合与提取出的需求ID逐一相同。

```bash
# 0. 一次取全部分支名、完整 ref、tip 日期（排除环境分支，见 §5）
git for-each-ref --format='%(refname:short)|%(refname)|%(authordate:short)' refs/remotes/origin refs/heads

# 0b.（可选但推荐）用远端真实分支列表与本地 ref 取交集
#     —— 本地 origin/* 是上次 fetch 的快照，远端已删分支会一直留着。
#     实测 pms-web 本地 99 个 ref vs 远端 25 个，74 个是幽灵分支。
git ls-remote --heads <repo>

# 1. 一个分支只跑一次：先用 -n 多取一条判断是否超限，输出行数即独占提交数
git log --first-parent -n <maxCommits+1> --format=%s origin/master..<branch>

# 2. 行为 0        → merged=true，不参与关联
#    行数 > maxCommits → skipped=true，commits=null（没数完，不编造数字）
#    否则提取需求ID，commits = 行数
```

**为什么区间可以直接写 `origin/master..<branch>`**：`--first-parent` 只沿第一父链前进，而分叉点（merge-base）本身在 master 上可达、会在遍历到它时被排除，因此结果与 `mb..<branch> --first-parent` 完全一致 —— 于是 merge-base 不必单独求。

**等价性验证方法**（改算法后必须重跑）：

```bash
mb=$(git merge-base origin/master "origin/$b")
diff <(git rev-list --first-parent "$mb..origin/$b" | sort) \
     <(git rev-list --first-parent "origin/master..origin/$b" | sort)
```

### 2.2 需求ID提取正则

```
跳过：不是纯 10 位（长度可配，默认 \d{10}）
提取：(^|[^0-9])([0-9]{10})([^0-9]|$)   → 捕获第 2 组
去重：按首次出现顺序保留
```

**为什么必须带数字边界**：`1234567890` 不得命中 `11234567890`。单测必须覆盖。

### 2.3 三个不可违背的约束（均由实测教训得出）

| # | 约束 | 违反后果（实测） |
|---|---|---|
| 1 | **必须 `--first-parent`** | 分支之间会互相 merge（`Merge branch 'feat/mdm三期分支' into feat/7000000010默认规则属性配置`），不加会把兄弟分支的工作算成自己的 |
| 2 | **必须排除基线**（用 `mb..branch`） | 直接 `git log <branch>` 会把从 dev/master 继承的上游提交全算进来：`feat/TextSearch组件优化` 冒出 9 个他人需求ID |
| 3 | **基线固定为发布主线**，不可用"独占提交最少"启发式 | 会把基线选到已吸收该分支的 dev 上：`feat/7000000010…` 从 256/80 变成 1/1，需求ID 全丢 |

### 2.4 基线选择的反例（2026-10-29 实测，用作防倒退用例）

| 分支 | base=master | base=dev | base=mdmdev |
|---|---|---|---|
| `pms-web feat/7000000010默认规则属性配置` | 全部 256 / fp **80** → ID `7000000006 7000000010` ✅ | 184 / 38 → 只剩 `7000000010` | **1 / 1 → 0 个 ID** ❌ |
| `ops-web feat/ops四需求合并分支` | 19 / fp **8** → 4 个 ID ✅ | 2 / 2 → 只剩 1 个 ❌ | 19 / 8 → 4 个 ✅ |

→ **实现必须固定用发布主线**。单测断言：任何情况下都不得以 dev 的结果作为输出。

## 3. L2：分支名匹配

```
对分支名 b、需求ID id：
  re = new RegExp('(^|[^0-9])' + id + '([^0-9]|$)')
  re.test(b)
```

**存在理由**：实测大量分支**分支名带 ID、但 commit message 未按规范写 ID**：

```
aps-web  feat/7000000001中台重构二期      message: "refactor(采购计划): 修改采购订单跳转逻辑"
scm-web  feat/7000000011费用单新增批量驳回按钮  message: "feat: 增加批量驳回功能并重构批量操作逻辑"
```

5 仓统计中 **L2 单独补位 14 个**（aps-web 一家 8 个），因此 **L2 不是 L1 的降级备选，必须并列执行后取并集**。

## 4. L3：人工关联

- 存储：`todo_branch_links[项目名\u0000分支名] = [需求ID, ...]`
- 入口：分支右键菜单「关联到需求…」、未登记分支卡片的「关联到需求」处置
- 与 `todo_branch_triage` 的 `action='linked'` 必须**同步写入**（两处语义一致，读时以 `branch_links` 为准）

## 5. 环境分支过滤（先于 L1/L2 执行）

```
默认排除（沿用现有正则）
  ^(master|test|dev|main|release|staging|hotfix|uat)(\b|_)

本次补充（默认，可配置为 envBranchPattern）
  ^(mdm)?(dev|uat|test|touat)$          // 实测每仓都存在：mdmdev / mdmuat / mdmtest / mdmtouat
  _old$ | _copy$ | ^(copy分支|复制分支)$  // 实测存在：dev_old / dev_copy / master_copy / test_copy / 复制分支
  ^origin$                              // 既有规则
```

**不在排除范围**（预期落入未登记分支列表）：

- `release-20260721`、`flx-0721`（auth-web）—— 发版批次分支
- `perf/integration`、`refactor/price-management` —— 技术重构分支

## 6. 并集合并与未登记判定

```
associate(需求ID, 项目) =
    L1: { b | workItemId ∈ index[b].ids }         // via='L1'
  ∪ L2: { b | 分支名数字边界命中 }                   // via='L2'
  ∪ L3: { b | branch_links[项目\0b] 含 workItemId } // via='L3'

unregistered(项目) =
    { b | index[b].commits > 0
        ∧ index[b].ids.length === 0
        ∧ L2 未命中任何已知需求ID
        ∧ triage[项目\0b] 不存在 }
```

排序权重（前端）：`commits × 活跃度`，活跃度按最近提交距今天数衰减；默认只展示 `commits ≥ minCommits(5)` 且 `近 activeWithinDays(90) 天有提交`。

## 8. 已知失效场景（明确不承诺）

| 场景 | 现状 | 兜底 |
|---|---|---|
| 提交信息完全没写需求ID 且分支名也没写 | L1/L2 皆空 | 归入未登记分支，人工 triage（如 `feat/mdm二期分支`） |
| 早期历史（规范落地前） | 同上 | 同上，一次 triage 后长期记忆 |
| 项目未本地 clone | 无法跑 L1 | 仅 L2；UI 必须标注「该项目无本地仓库，关联能力受限」 |
| 分支是 cherry-pick/rebase 拼成的 | `--first-parent` 可能带入外来提交 | 关联结果必须经预览确认，不自动落库 |
| 需求ID 长度变化（非 10 位） | 提取失败 | 正则长度作为配置项，可改 |

## 9. 性能与实现建议

- 实测 `git log --all --format=%s`（ops-web，915 条）**0.26s**；单仓 L1 全量预计 1~3s（40 个分支 × 3 次 git 调用）；
- 并发：项目维度并发 2~4，分支维度**串行**（避免磁盘 IO 抖动，实测收益不明显）；
- 缓存：`todo_branch_cache[项目].index` + `indexTimestamp`，TTL 10 分钟；
- 保护：`maxCommits` 超限跳过；同时最多一个反查在跑，重复请求回 `GIT_INDEX_BUSY`；
- 所有 `execFile` 传数组参数 + `--` 分隔 + `GIT_TERMINAL_PROMPT=0` + timeout。
