# 技术文档 · 本地 API 接口契约

> 配套：[技术方案-飞书需求同步与GitLab分支直读.md](./技术方案-飞书需求同步与GitLab分支直读.md)
> 范围：`server.js` 暴露的全部 HTTP 接口。前端 `todo-release.js` 是唯一调用方。

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| Base URL | `http://localhost:1949`（端口冲突会自动 +1，见 §5 已知缺陷） |
| 编码 | UTF-8，响应 `application/json; charset=utf-8` |
| CORS | 已全局放开 `Access-Control-Allow-Origin: *`，支持 `GET/POST/OPTIONS` |
| 方法 | 读操作 `GET`，带复杂入参的用 `POST` + JSON body |
| 错误格式 | 统一 `{ "error": "<人类可读中文>", "code": "<机器码>" }` |
| 错误判定 | **前端一律读 `body.code`，不看 HTTP status**（与公司后端习惯一致；实测后端业务失败常返 HTTP 200 + code） |
| 超时 | git 调用 15s；meegle CLI 调用 60s；均需 `AbortController`/`timeout` 兜底 |
| 缓存 | 进程内 LRU + TTL 10 分钟，键为「接口 + 关键参数」；`refresh=1` 强制绕过 |

### 1.1 错误码总表

| code | 建议 HTTP | 含义 | 触发条件 |
|---|---|---|---|
| `BAD_REQUEST` | 400 | 参数缺失或格式错误 | 必填参数为空、`repo` 与 `path` 都未给 |
| `GIT_REPO_INVALID` | 400 | `repo` 不是合法 `http(s)://` 地址 | 参数校验拦截（防 git 参数注入） |
| `GIT_PATH_MISSING` | 400 | `localPath` 不存在 | `fs.existsSync` 为假 |
| `GIT_NOT_REPO` | 400 | `localPath` 不是 git 仓库 | 无 `.git` 目录 |
| `GIT_TIMEOUT` | 504 | git 调用超时 | 15s 未结束 |
| `GIT_AUTH_REQUIRED` | 401 | 远端需要凭据且已禁止交互 | `GIT_TERMINAL_PROMPT=0` 下取不到凭据 |
| `GIT_INDEX_BUSY` | 503 | 同一项目已有反查在跑 | 并发保护，前端退避重试 |
| `MEEGLE_CLI_MISSING` | 500 | 找不到 meegle 可执行文件 | `spawn meegle.cmd` ENOENT |
| `MEEGLE_UNAUTH` | 401 | 未登录飞书项目 | `meegle auth status` 返回 `authenticated:false` |
| `MEEGLE_SPACE_NOT_FOUND` | 404 | 空间不存在 | `project search` 无命中 |
| `MEEGLE_SPACE_AMBIGUOUS` | 409 | 空间名多命中或无权限 | `project search` 命中 >1，**不得自动选** |
| `MEEGLE_NO_PERMISSION` | 403 | 当前身份对该空间无权限 | 接口回 Permission Denied |
| `MEEGLE_TIMEOUT` | 504 | CLI 调用超时 | 60s 未结束 |
| `MEEGLE_QUERY_FAILED` | 500 | MQL 执行失败 | 透传 CLI 的 `err_msg` |

### 2.1 `GET /api/git-user`

| 参数 | 必填 | 说明 |
|---|---|---|
| — | — | 无 |

```json
// 200
{ "user": "sunhui" }
// 200（取不到时不报错）
{ "user": null, "error": "无法获取git用户名" }
```

### 2.2 `GET /api/branches?path=<localPath>&user=<gitUser>`

走**本地 git 通道**（`git for-each-ref refs/remotes/origin/ refs/heads/`），返回带作者/日期的完整信息。

| 参数 | 必填 | 说明 |
|---|---|---|
| `path` | 是 | 项目本地绝对路径 |
| `user` | 否 | 按提交作者过滤，空则不筛 |

```json
// 200
{
  "path": "C:\\项目\\pms-web",
  "branches": [
    {
      "branch": "feat/7134246577业务呈现码调整",
      "author": "sunhui",
      "date": "2026-10-28",
      "message": "业务呈现码调整",
      "isRemote": true
    }
  ]
}
// 200（出错时也是 200，带 error 字段 —— 保持现状不改）
{ "error": "路径不存在", "path": "C:\\not-exist" }
```

**保持不变的要点**：出错仍返 200 + `error` 字段（现有前端依赖此形态）；排除 `origin` 及 `origin/` 前缀分支；保留环境分支过滤正则。

## 3. 新增接口 · GitLab 分支

### 3.1 `GET /api/git/branches`

两种模式二选一，**同时给出时 `repo` 优先**。

| 参数 | 必填 | 说明 |
|---|---|---|
| `repo` | 二选一 | GitLab 仓库地址，如 `https://git.joyintoy.cn/joyin/pms-web.git`（不带 `.git` 亦可，实测均通） |
| `path` | 二选一 | 本地路径，退回 §2.2 的本地通道 |
| `match` | 否 | 传给 `git ls-remote` 的 pattern，如 `*7101366806*` |
| `refresh` | 否 | `1` 时绕过缓存 |

```json
// 200 · ls-remote 模式
{
  "repo": "https://git.joyintoy.cn/joyin/pms-web.git",
  "source": "ls-remote",
  "cached": false,
  "elapsedMs": 1287,
  "branches": [{ "name": "feat/7134246577业务呈现码调整" }]
}
```

实现约束：

- 命令：`git ls-remote --heads <repo> [<match>]`，用 `execFile` 传数组参数，**绝不拼字符串**；
- 环境变量必须含 `GIT_TERMINAL_PROMPT=0`，否则无凭据时会挂死在交互式输入（实测过）；
- 超时 15s，超时杀进程并回 `GIT_TIMEOUT`；
- 在 `repo` 之前插 `--` 分隔符，防参数注入；
- 仅返回 `refs/heads/*`，剥掉前缀只留分支名。

### 3.2 `GET /api/git/branch-index`

核心接口：算「分支 → 覆盖的需求ID」反向索引，并标出未登记分支。

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `path` | 是 | — | 本地 git 仓库路径 |
| `repo` | 否 | — | 仓库地址。**给了就与远端真实分支列表取交集**，滤掉本地淘汰的陈旧 ref（见下方说明） |
| `base` | 否 | `master` | 发布主线 |
| `maxCommits` | 否 | `500` | 单分支独占提交数上限，超过则 `skipped: true` 且 `commits: null` |
| `maxBranches` | 否 | `300` | 单仓参与分析的分支数上限 |
| `onlyMine` | 否 | `1` | 只保留**我创建的分支**；传 `0` 则包含他人分支 |
| `refresh` | 否 | — | `1` 时绕过缓存 |

```json
// 200 · 2026-11-03 实测（ops-web）
{
  "path": "C:\\项目\\ops-web",
  "repo": "https://git.joyintoy.cn/joyin/ops-web",
  "base": "origin/master",
  "remoteFiltered": true,
  "total": 10,
  "scanned": 10,
  "localOnly": 34,
  "remoteOnly": [],
  "cached": false,
  "elapsedMs": 2316,
  "computedAt": 1762150000000,
  "branches": [
    {
      "name": "feat/ops四需求合并分支",
      "ids": ["7072591743", "6957065100", "7073079049", "7029460314", "7058457690"],
      "commits": 19,
      "lastDate": "2026-11-03",
      "merged": false,
      "skipped": false
    },
    { "name": "fix/渠道下拉框数据错误", "ids": [], "commits": 0, "lastDate": "2026-07-20", "merged": true, "skipped": false }
  ],
  "unregistered": [
    { "name": "feat/mdm二期分支", "commits": 28, "lastDate": "2026-09-21" }
  ]
}
```

**为什么需要 `repo`**：本地 `origin/*` 只是「上次 fetch 时的快照」，远端删掉的分支会一直留着。实测 pms-web 本地有 99 个 ref，远端实际只有 25 个 —— **74 个是幽灵分支**，其中未合并的会混进未登记列表和关联结果。传 `repo` 后，pms-web 从 91 个分析对象收敛到 17 个真实分支，而关键结论（`feat/ops四需求合并分支` = 19 提交 / 5 个需求ID）完全不变。

实现约束：

- 合并基线与提交计数**不再单独调用**：区间直接用 `origin/<base>..<分支>`。因为 `--first-parent` 只沿第一父链前进，而分叉点本身在主线可达、会被自然排除，结果与 `merge-base..分支 --first-parent` 逐一相同（已实测提交集合与提取出的 ID 均一致）。每分支因此只跑一次 git，28 个分支从 85 次调用降到 29 次，实测 6.4s → 2.9s；
- `-n (maxCommits + 1)`：既避免把超大分支的整段历史拉进内存，又不会把「刚好等于上限」的分支误判为超限；
- **创建者判定**：取该分支独占提交里**最早的一条**（最靠近分叉点）的作者，与 `git config user.name` / `user.email` 比对 —— 分支的起点作者才是创建者；别人建的分支上我后来补过几个提交，不该整条算成我的。实测 auth-web 的非主线分支全部属于他人（钱龙 / licheng / Liujiangbei），而 ops-web / pms-web / scm-web 的分支清一色是自己，所以这条过滤对后者零影响、对前者能清掉全部噪声；
- **身份取不到时不过滤**（`onlyMine` 回传 `false`）：否则会把所有分支都判成「不是我的」而静默清空整个索引，比不过滤危险得多；
- 远端列表拉取失败时**降级为纯本地分析**并置 `remoteFiltered: false`：提交分析本身不依赖网络，不该整体失败。

字段语义（前端按此渲染，不得二次推导）：

| 字段 | 语义 |
|---|---|
| `commits` | 该分支相对发布主线 **`--first-parent` 独占提交数**；`skipped: true` 时为 `null`（没数完，不编造数字） |
| `merged` | `commits === 0`，已完全并入主线，**不参与关联** |
| `skipped` | 独占提交数超过 `maxCommits`，未做 ID 提取；UI 必须与「确实没有 ID」区分 |
| `ids` | 去重后的 10 位需求ID，按首次出现顺序 |
| `unregistered` | `commits > 0` 且 `ids` 为空、且未被 triage 处置的分支 |
| `remoteFiltered` | 是否用远端分支列表做了交集（取决于是否传 `repo`） |
| `localOnly` | 被远端列表过滤掉的本地 ref 条数（诊断用，含 heads/remotes 重复项） |
| `remoteOnly` | 远端有、本地无 ref 的分支名（分析不了，提示该 fetch 了） |
| `onlyMine` | 本次是否按「我创建的」过滤（身份取不到时为 `false`，即未过滤） |
| `notMine` | 因不是自己创建而被滤掉的分支数 |
| `branches[].mine` | 是否我创建；未按创建者过滤（`onlyMine=0`）且身份未知时为 `null` |
| `branches[].owner` | 分支创建者（独占提交里最早一条的作者），用于展示「这是谁的分支」 |
| `computedAt` | 本次计算完成时间；缓存命中时据此判断结果新鲜度 |

⚠️ **结果有时效性**：实测 `feat/ops四需求合并分支` 在 10-29 是 fp=8/4个ID，11-02 变成 fp=18/5个ID。因此响应必须带 `elapsedMs` 且前端缓存需带 `timestamp`，TTL 到时自动重算。

## 4. 新增接口 · 飞书项目

### 4.1 `GET /api/meegle/status`

```json
// 200
{ "authenticated": false, "host": "project.feishu.cn", "reason": "no local token" }
// 200
{ "authenticated": true, "host": "project.feishu.cn", "expiresInMinutes": 42 }
```

实现：`meegle auth status --format json`，**按 CLI 返回的 `authenticated` 字段判定**，不要靠退出码（实测未登录时退出码为 1 但 JSON 结构完整）。

### 4.2 `GET /api/meegle/spaces`

```json
// 200
{
  "spaces": [
    { "projectKey": "6629becdcfea521fda9b97e4", "simpleName": "ly_oms", "name": "信息部工作汇总" }
  ]
}
```

### 4.3 `GET /api/meegle/types?projectKey=<key>`

```json
// 200
{
  "types": [
    { "apiName": "story", "typeKey": "story", "name": "OMS需求管理", "disabled": false },
    { "apiName": "oms", "typeKey": "662f70e94885b26530319f67", "name": "SCM需求管理", "disabled": false }
  ]
}
```

⚠️ **`typeKey` 才是 MQL 里的表名，而且常常不等于 `apiName`。** 实测 `ly_oms` 空间的 `oms` 类型，typeKey 是一串哈希；只有 `story` 恰好同名。拿 `apiName` 当表名会查错表 —— 要么报错，要么静默查回另一个类型的数据。前端必须先取元数据再拼 MQL。

### 4.4 `POST /api/meegle/query`

请求：

```json
{
  "projectKey": "6629becdcfea521fda9b97e4",
  "simpleName": "ly_oms",
  "types": [{ "apiName": "oms", "typeKey": "662f70e94885b26530319f67", "name": "SCM需求管理" }],
  "mqlTemplate": "SELECT `work_item_id`,`name`,`work_item_status` FROM `{space}`.`{type}`{statusFilter}",
  "excludeStatuses": ["已结束", "已上线"],
  "maxPerType": 200
}
```

响应：

```json
{
  "items": [
    {
      "workItemId": "7154016953",
      "name": "【MDM】【TMS关务税则对接】TMS关务税则获取SKU信息接口调整",
      "status": "开发中",
      "workItemType": "oms",
      "workItemTypeName": "SCM需求管理",
      "link": "https://project.feishu.cn/ly_oms/oms/detail/7154016953"
    }
  ],
  "perType": [{ "apiName": "oms", "name": "SCM需求管理", "count": 104, "fetched": 50, "excluded": ["已结束"] }],
  "errors": []
}
```

实现要点（全部为实测结论）：

- **一个空间里「需求管理」类工作项是按业务域拆成多张表的。** 实测 `ly_oms` 有 22 个工作项类型，其中需求管理类就有 10 个（OMS / SCM / TMS / BMS / BD / 仓库 / 优化 ×2 / 架构运维 / AI）。**只查一张表会静默漏掉其他域的全部需求** —— 所以本接口按类型数组循环，前端也必须多选；
- MQL 的 FROM 段：`{space}` 用 `simple_name`，`{type}` 用 `typeKey`。实测 `FROM \`ly_oms\`.\`story\`` 与 `FROM \`ly_oms\`.\`662f70e94885b26530319f67\`` 都可用；
- ⚠️ **`excludeStatuses` 必须按「类型 × 该类型的状态枚举」取交集后才能写进 WHERE。** 状态名是每个工作项类型各自一套的：实测 `story`（OMS需求管理）有 34 个状态（含「已上线」），`oms`（SCM需求管理）只有 17 个、**没有「已上线」**。MQL 里写了某类型不存在的状态值会直接返回 `ErrMetadataError / attribute value not found (Code 3011)`，**整个类型的查询失败**，而不是"匹配为空"。所以 server 先调 `workitem meta-fields --field-keys '["work_item_status"]'` 取该类型的真实 `option[].option_name`（缓存 1 小时），再与用户配置的排除清单求交集；交集为空则该类型不加 WHERE；
- 每个类型实际生效的排除项由 `perType[].excluded` 返回，前端据此显式展示（如 `已排除 已结束/已上线`），避免"以为排除了其实没排"；
- 状态枚举取自字段的 `option` 键（不是 `options`），元素形如 `{ option_id, option_name }`；
- **翻页协议**：首查传 `mql`，响应给 `session_id` + `list[0].count` + `list[0].group_infos[0].group_id`（无分组时 group_id 为 `"1"`）；第 2 页起只传 `--session-id` + `--group-pagination-list`，**不得再传 `mql`**（否则服务端按新查询重跑，翻页参数被忽略）。翻页响应里 `list` 为 `null`，**总数只能从首查拿**，由 server 缓存在本次循环里；
- 行结构是 `data[<group_id>][].moql_field_list[]`；字段值按 `value_type` 取 `string_value` / `long_value` / `key_label_value_list`（状态就是后者，取 `label`）；
- **单个类型失败不影响其他类型**：错误逐条进 `errors`，前端展示但不阻断整次同步（某个域没权限时不该让整批全废）；
- `link` 由 server 拼装：`https://project.feishu.cn/{simpleName}/{apiName}/detail/{workItemId}`。**路径段用的是 `apiName`，不是 `typeKey`** —— 已用 `meegle url decode` 反校验得到 `url_kind=workitem_detail`，字段一致；
- MQL 模板由前端下发（可编辑），server **不硬编码任何 MQL**。

### 4.5 实现注意（Windows）

```
✗ spawn('meegle', [...])                  → ENOENT（Windows 上只有 meegle.cmd）
✗ spawn('meegle.cmd', [...], { shell: true })
     → cmd.exe 会把参数里的 % 当变量展开，MQL 的 LIKE '%xxx%' 会被改坏
✓ spawn(process.execPath, [<.../@lark-project/meegle/bin/meegle.js>, ...args])
```

- 入口脚本定位顺序：`MEEGLE_JS` 环境变量 → `%APPDATA%\npm\node_modules\@lark-project\meegle\bin\meegle.js` → `C:\Program Files\nodejs\node_global\node_modules\@lark-project\meegle\bin\meegle.js`；都找不到才退回 `.cmd` + shell（能用但有转义风险）；
- 必须同时捕获 stdout 与 stderr（CLI 的错误信息走 stderr，只看到「退出码非 0」没法排障）；
- `--format json` 保证输出可解析；输出可能带日志前缀，解析前先裁到第一个 `{` / `[`；
- CLI 会把业务失败包在正常退出里，**必须检查 `err_msg` / `error` 字段**，不能只看退出码。

## 5. 新增接口 · 本地备份（v2.1）

数据只在浏览器 `localStorage` 里，清缓存/换机器就丢；「导出」还要用户自己挑目录、事后想不起存哪。
这组接口让引擎把备份直接写进**项目目录下的 `backup/`**，并负责列出与读取（恢复）。

备份目录：`<项目目录>/backup`（`server.js` 里的 `BACKUP_DIR`），已加入 `.gitignore`。

### 5.1 `POST /api/backup`

请求体：`{ "data": <导出格式的完整 JSON> }`（单请求体上限放宽到 32 MB，`items` 必须是数组，否则 `BAD_REQUEST`）。

响应 `200`：

```json
{
  "ok": true,
  "dir": "D:\\自研\\发版小助手-v2\\backup",
  "name": "todoList-发版需求-20261104134107.json",
  "file": "D:\\自研\\发版小助手-v2\\backup\\todoList-发版需求-20261104134107.json",
  "size": 34211,
  "items": 102,
  "at": 1793770867000
}
```

- 文件名由**服务端**生成（`todoList-发版需求-<yyyyMMddHHmmss>.json`），不接受客户端指定名字。
- 目录不存在时自动创建；写入用 `JSON.stringify(data, null, 2)` + UTF-8。
- 失败：`BACKUP_WRITE_FAILED`（500）。

### 5.2 `GET /api/backup/list`

响应 `200`：`{ dir, files: [{ name, size, mtime, items }] }`，按 `mtime` 倒序。`items` 从文件内容里读出来（解析失败为 `null`），列表里只看「哪天备份的、多少条」就能判断恢复哪份。目录不存在时返回空数组而不是报错。

### 5.3 `GET /api/backup/read?name=<文件名>`

返回该备份的原始 JSON（即导出格式），供前端恢复。`name` 必须是**备份目录下的单个 `.json` 文件名**：先 `path.basename(name) === name`，再校验拼接结果落在 `BACKUP_DIR` 之内，否则 `BAD_REQUEST`（防路径穿越）。文件不存在为 `BACKUP_NOT_FOUND`（404）。

### 5.4 `POST /api/backup/reveal`

在资源管理器里打开备份目录（win32 用 `explorer.exe`，macOS 用 `open`，其余 `xdg-open`）。响应 `{ ok: true, dir }`。桌面环境下 explorer 打开成功也可能返回非 0 退出码，所以不判定退出码。

## 6. 新增接口 · 版本与一键更新（v2.1）

页面就是这个 git 仓库里的静态文件，所以在项目目录里 `git pull` 就等于「更新应用」，
不必像浏览器插件那样另做一套分发。三个前提决定了接口形态：

1. 私有仓库需要登录 GitHub，而引擎**不做交互式提示**（`GIT_TERMINAL_PROMPT=0`，否则会挂死），
   所以「没登录」必须作为一种**独立结果**回报，而不是当成「没有更新」；
2. `server.js` 已经加载在进程里：这次更新若动了引擎代码，刷新页面没用，必须重启 —— 接口要告诉前端；
3. 本地有未提交改动时不得更新，否则会把人工改动卷进合并。

### 6.1 `GET /api/version`

返回当前提交，页面用它渲染版本徽标。

```json
{ "commit": "d602cb0", "full": "d602cb0...", "date": "2026-11-04 13:44",
  "subject": "feat(...): ...", "branch": "master",
  "remote": "https://github.com/sunshine1130/release-pilot-v2.git", "dirty": false }
```

### 6.2 `GET /api/update/check`

`git fetch --prune origin`（60s 超时）后比对 `HEAD...origin/<branch>`。响应分三种：

| 情形 | 响应要点 |
|---|---|
| 不是 git 仓库 / 没有 origin | `{ configured: false, local, hint }` |
| fetch 失败（没登录、仓库不存在、断网） | `{ configured: true, reachable: false, local, error }`，登录失败给专门的登录指引文案 |
| fetch 成功 | `{ configured: true, reachable: true, local, remoteLatest, ahead, behind, dirty, hasUpdate }`，`hasUpdate = behind > 0`；远端没有该分支时给 `{ hasUpdate: false, hint }` |

> 关键设计：**拉不到 ≠ 有更新**。三种结果分开回报，前端就不会在断网时提示「发现新版本」。

### 6.3 `POST /api/update/apply`

`git pull --ff-only origin <branch>`（60s 超时），并比对 `git diff --name-only <old>..<new>`。

- 本地有未提交改动：`UPDATE_DIRTY`（409），不执行拉取；
- 拉取需要登录：`UPDATE_AUTH_REQUIRED`，文案引导用户先手工 `git pull` 登录一次；
- 分叉（非 fast-forward）或其他失败：`UPDATE_FAILED`；
- 成功：`{ ok: true, from, to, subject, files, engineChanged }`。

`engineChanged = files 含 server.js`，前端据此决定「自动刷新页面」还是「提示重启 start-server.bat」。

## 7. 已知缺陷与顺带修复

### 7.1 端口漂移导致前端失联（**已修复**）

`server.js` 在 `EADDRINUSE` 时会自动重试 `port + 1`，而原本前端把 `API_PORT = 1949` 写死，一旦漂移，所有请求都会打到别的进程上且没有任何提示。

已按方案 A 修复：server 启动成功后把实际端口写入 `./.server-port`，前端启动先 `fetch('./.server-port')`，读不到再退回 1949（旧引擎不写该文件，属正常情况）。

**这不是理论风险**：开发时本机 1949 一直被旧版服务占着，v2 每次都落到 1950 —— 修复前后端确实是「按钮点了没反应」，修复后正常。

> 补充（v2.1）：端口漂移不只是换个地址。`localStorage` 按「协议+主机+端口」隔离，换端口等于换一份数据。
> 页头现在会在端口非默认时显示徽标说明此事，否则用户只会以为数据丢了。

### 7.2 环境分支过滤不全

现有正则 `^(master|test|dev|main|release|staging|hotfix|uat)(\b|_)` 挡不住 `mdmdev` / `mdmuat` / `mdmtest` / `mdmtouat`（实测这几个在每个仓库都存在）。补充规则见方案文档 §6.4。

> 注意：`release-20260721`、`flx-0721`（auth-web 实测存在）属于**发版批次分支**，不在排除范围，会落入「未登记分支」列表——这是预期行为。
