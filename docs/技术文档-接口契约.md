# 技术文档 · 本地 API 接口契约

> 配套：[技术方案-飞书需求同步与GitLab分支直读.md](./技术方案-飞书需求同步与GitLab分支直读.md)
> 范围：`server.js` 暴露的全部 HTTP 接口。前端 `todo-release.js` 是唯一调用方。

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| Base URL | `http://localhost:1949`（端口冲突会自动 +1，见 §5 已知缺陷） |
| 编码 | UTF-8，响应 `application/json; charset=utf-8` |
| CORS | 已全局放开 `Access-Control-Allow-Origin: *`，支持 `GET/POST/OPTIONS` |
| 方法 | 读操作 `GET`，带复杂入参的用 `POST` + JSON body |
| 错误格式 | 统一 `{ "error": "<人类可读中文>", "code": "<机器码>" }` |
| 错误判定 | **前端一律读 `body.code`，不看 HTTP status**（与公司后端习惯一致；实测后端业务失败常返 HTTP 200 + code） |
| 超时 | git 调用 15s；meegle CLI 调用 60s；均需 `AbortController`/`timeout` 兜底 |
| 缓存 | 进程内 LRU + TTL 10 分钟，键为「接口 + 关键参数」；`refresh=1` 强制绕过 |

### 1.1 错误码总表

| code | 建议 HTTP | 含义 | 触发条件 |
|---|---|---|---|
| `BAD_REQUEST` | 400 | 参数缺失或格式错误 | 必填参数为空、`repo` 与 `path` 都未给 |
| `GIT_REPO_INVALID` | 400 | `repo` 不是合法 `http(s)://` 地址 | 参数校验拦截（防 git 参数注入） |
| `GIT_PATH_MISSING` | 400 | `localPath` 不存在 | `fs.existsSync` 为假 |
| `GIT_NOT_REPO` | 400 | `localPath` 不是 git 仓库 | 无 `.git` 目录 |
| `GIT_TIMEOUT` | 504 | git 调用超时 | 15s 未结束 |
| `GIT_AUTH_REQUIRED` | 401 | 远端需要凭据且已禁止交互 | `GIT_TERMINAL_PROMPT=0` 下取不到凭据 |
| `GIT_INDEX_BUSY` | 503 | 同一项目已有反查在跑 | 并发保护，前端退避重试 |
| `MEEGLE_CLI_MISSING` | 500 | 找不到 meegle 可执行文件 | `spawn meegle.cmd` ENOENT |
| `MEEGLE_UNAUTH` | 401 | 未登录飞书项目 | `meegle auth status` 返回 `authenticated:false` |
| `MEEGLE_SPACE_NOT_FOUND` | 404 | 空间不存在 | `project search` 无命中 |
| `MEEGLE_SPACE_AMBIGUOUS` | 409 | 空间名多命中或无权限 | `project search` 命中 >1，**不得自动选** |
| `MEEGLE_NO_PERMISSION` | 403 | 当前身份对该空间无权限 | 接口回 Permission Denied |
| `MEEGLE_TIMEOUT` | 504 | CLI 调用超时 | 60s 未结束 |
| `MEEGLE_QUERY_FAILED` | 500 | MQL 执行失败 | 透传 CLI 的 `err_msg` |

## 2. 已有接口（行为保持不变）

> 这两个接口是现有工具的命脉，本次改造**不得改变其响应结构**。

### 2.1 `GET /api/git-user`

| 参数 | 必填 | 说明 |
|---|---|---|
| — | — | 无 |

```json
// 200
{ "user": "sunhui" }
// 200（取不到时不报错）
{ "user": null, "error": "无法获取git用户名" }
```

### 2.2 `GET /api/branches?path=<localPath>&user=<gitUser>`

走**本地 git 通道**（`git for-each-ref refs/remotes/origin/ refs/heads/`），返回带作者/日期的完整信息。

| 参数 | 必填 | 说明 |
|---|---|---|
| `path` | 是 | 项目本地绝对路径 |
| `user` | 否 | 按提交作者过滤，空则不筛 |

```json
// 200
{
  "path": "C:\\项目\\pms-web",
  "branches": [
    {
      "branch": "feat/7134246577业务呈现码调整",
      "author": "sunhui",
      "date": "2026-10-28",
      "message": "业务呈现码调整",
      "isRemote": true
    }
  ]
}
// 200（出错时也是 200，带 error 字段 —— 保持现状不改）
{ "error": "路径不存在", "path": "C:\\not-exist" }
```

**保持不变的要点**：出错仍返 200 + `error` 字段（现有前端依赖此形态）；排除 `origin` 及 `origin/` 前缀分支；保留环境分支过滤正则。

## 3. 新增接口 · GitLab 分支

### 3.1 `GET /api/git/branches`

两种模式二选一，**同时给出时 `repo` 优先**。

| 参数 | 必填 | 说明 |
|---|---|---|
| `repo` | 二选一 | GitLab 仓库地址，如 `https://git.joyintoy.cn/joyin/pms-web.git`（不带 `.git` 亦可，实测均通） |
| `path` | 二选一 | 本地路径，退回 §2.2 的本地通道 |
| `match` | 否 | 传给 `git ls-remote` 的 pattern，如 `*7101366806*` |
| `refresh` | 否 | `1` 时绕过缓存 |

```json
// 200 · ls-remote 模式
{
  "repo": "https://git.joyintoy.cn/joyin/pms-web.git",
  "source": "ls-remote",
  "cached": false,
  "elapsedMs": 1287,
  "branches": [{ "name": "feat/7134246577业务呈现码调整" }]
}
```

实现约束：

- 命令：`git ls-remote --heads <repo> [<match>]`，用 `execFile` 传数组参数，**绝不拼字符串**；
- 环境变量必须含 `GIT_TERMINAL_PROMPT=0`，否则无凭据时会挂死在交互式输入（实测过）；
- 超时 15s，超时杀进程并回 `GIT_TIMEOUT`；
- 在 `repo` 之前插 `--` 分隔符，防参数注入；
- 仅返回 `refs/heads/*`，剥掉前缀只留分支名。

### 3.2 `GET /api/git/branch-index`

核心接口：算「分支 → 覆盖的需求ID」反向索引，并标出未登记分支。

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `path` | 是 | — | 本地 git 仓库路径 |
| `repo` | 否 | — | 仓库地址。**给了就与远端真实分支列表取交集**，滤掉本地淘汰的陈旧 ref（见下方说明） |
| `base` | 否 | `master` | 发布主线 |
| `maxCommits` | 否 | `500` | 单分支独占提交数上限，超过则 `skipped: true` 且 `commits: null` |
| `maxBranches` | 否 | `300` | 单仓参与分析的分支数上限 |
| `refresh` | 否 | — | `1` 时绕过缓存 |

```json
// 200 · 2026-11-03 实测（ops-web）
{
  "path": "C:\\项目\\ops-web",
  "repo": "https://git.joyintoy.cn/joyin/ops-web",
  "base": "origin/master",
  "remoteFiltered": true,
  "total": 10,
  "scanned": 10,
  "localOnly": 34,
  "remoteOnly": [],
  "cached": false,
  "elapsedMs": 2316,
  "computedAt": 1762150000000,
  "branches": [
    {
      "name": "feat/ops四需求合并分支",
      "ids": ["7072591743", "6957065100", "7073079049", "7029460314", "7058457690"],
      "commits": 19,
      "lastDate": "2026-11-03",
      "merged": false,
      "skipped": false
    },
    { "name": "fix/渠道下拉框数据错误", "ids": [], "commits": 0, "lastDate": "2026-07-20", "merged": true, "skipped": false }
  ],
  "unregistered": [
    { "name": "feat/mdm二期分支", "commits": 28, "lastDate": "2026-09-21" }
  ]
}
```

**为什么需要 `repo`**：本地 `origin/*` 只是「上次 fetch 时的快照」，远端删掉的分支会一直留着。实测 pms-web 本地有 99 个 ref，远端实际只有 25 个 —— **74 个是幽灵分支**，其中未合并的会混进未登记列表和关联结果。传 `repo` 后，pms-web 从 91 个分析对象收敛到 17 个真实分支，而关键结论（`feat/ops四需求合并分支` = 19 提交 / 5 个需求ID）完全不变。

实现约束：

- 合并基线与提交计数**不再单独调用**：区间直接用 `origin/<base>..<分支>`。因为 `--first-parent` 只沿第一父链前进，而分叉点本身在主线可达、会被自然排除，结果与 `merge-base..分支 --first-parent` 逐一相同（已实测提交集合与提取出的 ID 均一致）。每分支因此只跑一次 git，28 个分支从 85 次调用降到 29 次，实测 6.4s → 2.9s；
- `-n (maxCommits + 1)`：既避免把超大分支的整段历史拉进内存，又不会把「刚好等于上限」的分支误判为超限；
- 远端列表拉取失败时**降级为纯本地分析**并置 `remoteFiltered: false`：提交分析本身不依赖网络，不该整体失败。

字段语义（前端按此渲染，不得二次推导）：

| 字段 | 语义 |
|---|---|
| `commits` | 该分支相对发布主线 **`--first-parent` 独占提交数**；`skipped: true` 时为 `null`（没数完，不编造数字） |
| `merged` | `commits === 0`，已完全并入主线，**不参与关联** |
| `skipped` | 独占提交数超过 `maxCommits`，未做 ID 提取；UI 必须与「确实没有 ID」区分 |
| `ids` | 去重后的 10 位需求ID，按首次出现顺序 |
| `unregistered` | `commits > 0` 且 `ids` 为空、且未被 triage 处置的分支 |
| `remoteFiltered` | 是否用远端分支列表做了交集（取决于是否传 `repo`） |
| `localOnly` | 被远端列表过滤掉的本地 ref 条数（诊断用，含 heads/remotes 重复项） |
| `remoteOnly` | 远端有、本地无 ref 的分支名（分析不了，提示该 fetch 了） |
| `computedAt` | 本次计算完成时间；缓存命中时据此判断结果新鲜度 |

⚠️ **结果有时效性**：实测 `feat/ops四需求合并分支` 在 10-29 是 fp=8/4个ID，11-02 变成 fp=18/5个ID。因此响应必须带 `elapsedMs` 且前端缓存需带 `timestamp`，TTL 到时自动重算。

## 4. 新增接口 · 飞书项目

### 4.1 `GET /api/meegle/status`

```json
// 200
{ "authenticated": false, "host": "project.feishu.cn", "reason": "no local token" }
// 200
{ "authenticated": true, "host": "project.feishu.cn", "expiresInMinutes": 42 }
```

实现：`meegle auth status --format json`，**按 CLI 返回的 `authenticated` 字段判定**，不要靠退出码（实测未登录时退出码为 1 但 JSON 结构完整）。

### 4.2 `GET /api/meegle/spaces?q=<关键字>`

```json
// 200
{
  "spaces": [{ "projectKey": "6xxxxx", "simpleName": "mdm", "name": "MDM中台" }],
  "ambiguous": false
}
```

- 空 `q` → 返回当前用户最近访问的空间列表；
- 命中 >1 时 `ambiguous: true`，**前端必须让用户选，不得自动取第一个**（同名空间可能存在且无权限，见错误码 `MEEGLE_SPACE_AMBIGUOUS`）。

### 4.3 `POST /api/meegle/query`

请求：

```json
{
  "projectKey": "6xxxxx",
  "workItemType": "story",
  "mql": "SELECT name, status FROM story WHERE ...",
  "sessionId": null,
  "pageNum": 1
}
```

响应：

```json
{
  "count": 128,
  "sessionId": "a1b2c3",
  "pageNum": 1,
  "items": [
    {
      "workItemId": "7134246577",
      "workItemType": "story",
      "name": "业务呈现码调整",
      "status": "进行中",
      "completed": false,
      "link": "https://project.feishu.cn/mdm/story/detail/7134246577",
      "owners": ["sunhui"]
    }
  ]
}
```

**翻页协议（必须遵守 CLI 的约定）**：

| 阶段 | 传参 | 说明 |
|---|---|---|
| 首查 | `projectKey` + `mql` | 返回第 1 页（≤50 条）+ `count` + `sessionId` |
| 后续页 | `projectKey` + `sessionId` + `pageNum` | **不得再传 `mql`**，否则服务端会当作新查询重跑、翻页参数被忽略 |

- 第 N 页（N≥2）响应里 `count` / `sessionId` 为 null，**总数只能从首查拿** → server 需把首查的 `count`/`sessionId` 缓存在会话里一并回给前端；
- `link` 由 server 拼装：`https://project.feishu.cn/{simpleName}/{workItemType}/detail/{workItemId}`；上线前用 `meegle url decode --url <链接>` 反校验一次 `url_kind === 'workitem_detail'`，**校验不过就不返回该链接**；
- `completed` 由 `status` 字段（type = `_work_item_status`）推导，前端据此在预览里标注"飞书状态：已完成"；
- MQL 文本由前端下发（可编辑配置），server **不硬编码任何 MQL**。

### 4.4 实现注意（Windows）

```
✗ spawn('meegle', [...])           → ENOENT（Windows 上是 meegle.cmd）
✓ spawn('meegle.cmd', [...], { shell: false, stdio: 'pipe' })
✓ 或 spawn(process.execPath, [path.join(npmGlobal,'node_modules/@larksuite/.../bin.js'), ...])
```

- 必须捕获 stdout 与 stderr 两个流，CLI 的错误信息走 stderr；
- `--format json` 保证输出可解析；输出可能带 ANSI 或日志前缀，解析前先裁到第一个 `{`/`[`。

## 5. 已知缺陷与顺带修复

### 5.1 端口漂移导致前端失联（现存缺陷）

`server.js` 的 `startServer(port)` 在 `EADDRINUSE` 时会自动重试 `port + 1`，但 `todo-release.js` 里 `API_PORT = 1949` 是**硬编码**。一旦 1949 被占，服务实际跑在 1950，前端所有请求全部打空，且没有任何提示。

建议修复（二选一）：

- **方案 A（推荐）**：server 启动成功后把实际端口写入 `./.server-port`，前端启动时先 `fetch('./.server-port')` 读取；
- **方案 B**：前端对 `1949..1955` 依次探测 `/api/git-user`，第一个通的即为有效端口并记住。

### 5.2 环境分支过滤不全

现有正则 `^(master|test|dev|main|release|staging|hotfix|uat)(\b|_)` 挡不住 `mdmdev` / `mdmuat` / `mdmtest` / `mdmtouat`（实测这几个在每个仓库都存在）。补充规则见方案文档 §6.4。

> 注意：`release-20260721`、`flx-0721`（auth-web 实测存在）属于**发版批次分支**，不在排除范围，会落入「未登记分支」列表——这是预期行为。

## 6. 接口调用时序（前端一次完整同步）

```
前端                                 server.js
 │  GET /api/meegle/status ──────────▶  meegle auth status
 │  ◀── { authenticated, host }
 │  POST /api/meegle/query (首查) ───▶  meegle workitem query --mql
 │  ◀── { items, count, sessionId }
 │  POST /api/meegle/query (第2..N页, 带 sessionId)
 │  ◀── { items, count:null, sessionId:null }   ← server 补齐首查的 count/sessionId
 │
 │  GET /api/git/branch-index?path=… ─▶  for-each-ref + merge-base + log --first-parent
 │  ◀── { branches:[{name,ids,commits,…}], unregistered:[…] }
 │
 │  （前端本地完成：去重 / L1∪L2∪L3 关联 / 未登记判定 / 预览渲染）
```
