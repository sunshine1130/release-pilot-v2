## 1. 存储全景

**全部数据都在浏览器 `localStorage` 里**（按「协议+主机+端口」隔离，换端口等于换一份数据），服务端不存业务数据；
唯一落盘的业务数据是「备份」按钮写出的 `backup/` 文件（见 §1.1）。

| 键名 | 状态 | 内容 | 写入时机 | 随导出走 |
|---|---|---|---|---|
| `todo_release_data` | 已有，**结构扩字段** | 需求列表 `Item[]` | 需求增删改、状态流转 | ✅ |
| `todo_project_names` | 已有，**结构扩字段** | 项目列表 `Project[]` | 项目增删改 | ✅ |
| `todo_launch_branch` | 已有，**不变** | 字符串，全局上线分支 | 保存上线分支 | ✅ |
| `todo_branch_cache` | 已有，**结构扩字段** | 分支缓存 `{ [项目名]: ProjectCache }` | 获取分支/反查后 | ✅ |
| `todo_last_branch_fetch_date` | 已有，**不变** | `YYYY-MM-DD`，自动抓取去重 | 每日自动抓取后 | ❌ |
| `todo_last_remind_date` | 已有，**不变** | `YYYY-MM-DD`，备份提醒去重 | 关闭提醒弹窗 | ❌ |
| `todo_branch_links` | v2 新增 | L3 人工关联记忆 `{ [键]: string[] }` | 手工关联分支↔需求（界面待补） | ✅ |
| `todo_branch_triage` | v2 新增 | 未登记分支处置 `{ [键]: TriageRecord }` | 三种处置操作 | ✅ |
| `todo_meegle_config` | v2 新增 | 飞书同步配置（空间/类型/MQL 模板/排除状态） | 同步设置弹窗保存 | ✅ |
| `todo_branch_index` | v2 新增 | 分支索引 `{ [项目名]: { branches, unregistered, ... } }`，10 分钟有效 | 刷新/自动补算索引 | ❌ 派生数据 |
| `todo_index_config` | v2 新增 | 索引口径 `{ onlyMine }` | 「只看我的分支」开关 | ✅ |

**复合键约定**：凡以「项目名 + 分支名」为键的地方，统一用 `项目名 + '\u0000' + 分支名` 拼接（沿用现有 `getReleasedBranchSet()` 的写法，避免用可能出现在名字里的分隔符）。

**写入纪律**：现有 `saveToLocalStorage()` / `saveBranchCache()` / `saveLaunchBranch()` 三个函数继续承担写入职责，新增键各自配一个 save 函数，**不要新增统一的 saveAll**（现有代码在多处细粒度调用，改成全量会引入无谓写放大）。

### 1.1 服务端 `backup/` 目录（v2.1）

「导出」是浏览器下载，用户得自己挑目录、事后想不起存哪。备份改由引擎写盘，固定在项目目录下：

```
D:\自研\发版小助手-v2\backup\todoList-发版需求-20261104134107.json
```

- 文件名由服务端生成，格式 `todoList-发版需求-<yyyyMMddHHmmss>.json`；内容与「导出」完全相同（`getFullData()`）。
- **不含 `todo_branch_index`**：它是能从 git 重算的派生数据，备份里带上只会变成过期快照。恢复后点「刷新分支索引」即可。
- 目录已加入 `.gitignore`（里面有真实需求数据，不该进版本管理）。
- 前端「备份记录」弹窗通过 `GET /api/backup/list` 列出、`GET /api/backup/read` 恢复；恢复是覆盖性写入，因此要点两次确认。
- 每日提醒的「备份保存」优先走这条路（引擎没起时才退回下载导出）。接口契约见 [接口契约 §5](技术文档-接口契约.md)。

## 2. 数据模型

### 2.1 Item（需求）

```js
{
  id: 'l9k2x4ab',                  // 既有：Date.now().toString(36)+随机，保持不变
  name: '业务呈现码调整',
  link: 'https://project.feishu.cn/mdm/story/detail/7134246577',
  status: 'new' | 'pending' | 'releasing' | 'released',
  projects:     [{ name: 'pms-web', branch: 'feat/7134246577业务呈现码调整', notes: '' }],
  syncBranches: [{ project: 'base-web', branch: 'feat/xxx', notes: '' }],
  targetBranches: { 'pms-web': 'mdmuat' },   // 可选
  releaseTime: '2026-10-29 11:03:58',        // 可选，YYYY-MM-DD HH:mm:ss

  // ↓↓↓ 本次新增，全部可选；旧数据没有这些字段，逻辑必须容忍 undefined ↓↓↓
  source: {                                  // 来自飞书项目的溯源信息
    provider: 'meegle',
    projectKey: '6xxxxx',
    simpleName: 'mdm',
    workItemType: 'story',
    workItemId: '7134246577',
    syncedAt: 1761700000000
  },
  branchLinks: [                             // 分支关联来源，用于 UI 标注与影响面
    { project: 'pms-web', branch: 'feat/7134246577业务呈现码调整', via: 'L1', alsoIds: [] }
  ]
}
```

**`via` 取值**（关联来源，UI 据此决定标签样式与文案）：

| 值 | 含义 | UI 表现 |
|---|---|---|
| `L1` | 分支 first-parent 独占提交反查命中 | 实心标签「反查」 |
| `L2` | 分支名含需求ID | 虚线标签「分支名（推断）」 |
| `L3` | 人工关联 | 标签「手工」 |
| `L1+L2` / `L1+L3` … | 多路同时命中 | 取最高置信，另加角标 N |

**`alsoIds`**：该分支覆盖的**其他**需求ID（来自 `branchRead.index[branch].ids` 去掉自己）。用于渲染「此分支还服务：xxx」的影响面提示。

> 注意：`alsoIds` 是**运行时由索引算出来的展示字段**，可以不持久化；若持久化则导入后需按最新索引重算，避免陈旧。

### 2.2 Project（项目）

```js
{
  name: 'pms-web',
  mr: 'https://git.joyintoy.cn/joyin/pms-web',   // 既有：MR 基础地址
  localPath: 'C:\\项目\\pms-web',                 // 既有：本地路径，可选
  repo: ''                                        // 新增：仓库地址，空则从 mr 推导，可选
}
```

**`deriveRepoUrl(mr)` 规则**（纯函数，需单测）：

```
输入 mr = 'https://git.joyintoy.cn/joyin/pms-web/-/merge_requests/new?x=1'
1. 去掉 query（? 之后）与 hash
2. 若含 '/-/merge_requests' → 截断到该段之前
   否则若含 '/merge_requests' → 截断到该段之前
3. 去掉末尾所有 '/'
4. 追加 '.git'
输出 'https://git.joyintoy.cn/joyin/pms-web.git'
```

边界：`mr` 为空 → 返回 `''`；已是 `.git` 结尾 → 不重复追加；非 `http(s)://` → 返回 `''`（由调用方跳过该项目）。

### 2.3 ProjectCache（分支缓存条目）

```js
// localStorage['todo_branch_cache']['pms-web']
{
  // 既有字段（本地通道，保持原样）
  branches: [{ branch, author, date, message, isRemote }],
  timestamp: 1761700000000,

  // 新增（全部可选，读取时按存在性判断通道）
  names: ['feat/7134246577业务呈现码调整', ...],   // ls-remote 通道：只有名字
  repo: 'https://git.joyintoy.cn/joyin/pms-web.git',
  source: 'ls-remote' | 'local',                   // 本条目数据来自哪条通道
  base: 'origin/master',                           // L1 反查用的基线
  index: {                                         // 分支 → 覆盖的需求
    'feat/ops四需求合并分支': {
      ids: ['6957065100','7029460314','7058457690','7072591743','7073079049'],
      commits: 18, lastDate: '2026-11-02', merged: false, skipped: false
    }
  },
  unregistered: ['feat/mdm二期分支', ...],          // 未登记分支名（详情从 index 取）
  indexTimestamp: 1761700000000                     // 反查时间，用于 TTL 判定
}
```

**双通道共存规则**：`branches` 与 `names` 可同时存在。UI 展示优先用 `branches`（有作者/日期）；只有 `names` 时降级为纯名字列表。**不得因存在 `names` 就丢弃 `branches`。**

### 2.4 IntegrationConfig（新增键 `todo_integration_config`）

```js
{
  meegle: {
    projectKey: '6xxxxx',
    simpleName: 'mdm',
    workItemType: 'story',
    mql: 'SELECT name, status FROM story WHERE ...',
    extraFields: ['status']          // 需要从飞书额外取的字段 key
  },
  projects: ['pms-web', 'aps-web', 'scm-web', 'auth-web', 'ops-web'],  // 参与匹配的项目名
  baseBranch: 'master',               // 发布主线（L1 基线）
  envBranchPattern: '^(mdm)?(dev|uat|test|touat)$',  // 环境分支排除，用户可改
  unregisteredFilter: {
    minCommits: 5,                    // 未登记分支展示阈值
    activeWithinDays: 90
  }
}
```

### 2.5 TriageRecord（新增键 `todo_branch_triage`）

```js
// key: 'aps-web\u0000feat/mdm二期分支'
{
  action: 'linked' | 'exempt' | 'ignored',
  ids: ['7134246577'],     // action='linked' 时该分支服务的需求ID
  at: 1761700000000,
  note: '需求未出，先跟着 mdm 二期一起发'   // 可选，人工备注
}
```

| action | 语义 | 后续行为 |
|---|---|---|
| `linked` | 关联到需求（等价 L3，会同步写 `todo_branch_links`） | 参与正常发版流程，退出未登记列表 |
| `exempt` | 无需需求（纯技术重构/环境调整） | 退出未登记列表；若该分支被选入某需求会提示"已标记为无需需求" |
| `ignored` | 不再关心 | 永久退出未登记列表，不提示 |

## 3. 去重与合并规则

### 3.1 需求去重

**唯一键**：`source.provider + ':' + source.workItemId`。

| 情况 | 处理 |
|---|---|
| 本地无同键 | 新增，`status` 固定为 `'new'` |
| 本地有同键 | 归入「已存在」，**默认不覆盖**；用户可勾「仅更新标题/链接」（只改 `name`/`link`，不动 `projects`/`status`/`releaseTime`） |
| 飞书已关闭（`completed: true`） | 预览里标注，**不自动删、不自动改状态** |
| 本地手工新增的需求（无 `source`） | 永不参与去重匹配，不受同步影响 |

### 3.2 分支关联合并

```
associate(item) =
    { (project, branch) | branch ∈ branchIndex[project] 且 workItemId ∈ branchIndex[project][branch].ids }   // L1
  ∪ { (project, branch) | branch 名数字边界命中 workItemId }                                                 // L2
  ∪ { (project, branch) | todo_branch_links[project\0branch] 含 workItemId }                                 // L3
```

- 按 `(project, branch)` 去重，`via` 取并集（多路命中则记为 `L1+L2` 形式）；
- 结果**默认只做展示与预填**，必须经用户确认才写入 `item.projects`；
- 同一 `workItemId` 命中多个分支时，默认选 **L1 命中且 `commits` 最小**的那条（越专一越可能是主分支），其余折叠为「另有 N 个」。

## 4. 导出 / 导入兼容性

### 4.1 导出

`exportToFile()` 经 `getFullData()` 输出：

```js
{
  projectNames: [...],      // 既有
  items: [...],             // 既有，本次 item 上多出 source / branchLinks
  branchesCache: {...},     // 既有，条目上多出 names / index / unregistered
  launchBranch: '...'       // 既有
}
```

**规则**：只增字段，不删不改既有字段的语义；`filename` 格式 `todoList-发版需求-{YYYYMMDDHHmmss}.json` 不变。

### 4.2 导入兼容矩阵

| 导入的文件 | 行为 |
|---|---|
| 旧版（无 `source`/`index` 等新字段） | 完全正常。缺失字段按 `undefined` 处理，关联功能在下次刷新索引后自然生效 |
| 新版 | 正常。`indexTimestamp` 过期则后台重算，不阻塞渲染 |
| 缺 `projectNames` 但状态为 `releasing` 的需求引用了未知项目 | 保留数据不删；`getProjectInfo()` 返回 undefined 的既有兜底逻辑继续生效（标签退化为无色、不可点击） |
| 非法 JSON | `toast('导入失败：JSON 格式错误')`，保持现状 |

### 4.3 迁移策略：**不做显式迁移**

- 不写 upgrade 函数，不引入 schema version 字段；
- 新字段一律**惰性补全**：首次需要时（如首次反查、首次同步）才写入；
- 理由：这是本机个人工具，用户可能随时用旧导出文件覆盖；任何"迁移"都可能与覆盖操作打架。

## 5. 索引时效性（实测教训）

实测同一分支的需求覆盖会随时间变化：

| 时间 | `ops-web feat/ops四需求合并分支` | `scm-web feat/7128829743…` |
|---|---|---|
| 2026-10-29 | fp=8，L1 = 4 个 ID | fp=1，**L1 为空**（仅 L2 命中） |
| 2026-11-03 | fp=18，L1 = **5** 个 ID | fp=2，**L1 = 1 个 ID** |

因此：

1. `index` 必须带 `indexTimestamp`，**TTL 10 分钟**；过期后自动重算，不得无限期复用；
2. 用户手工点「刷新分支索引」可强制重算；
3. 任何"关联结果"在写入 `item.projects` 前必须重新校验一次索引新鲜度（或至少提示「索引更新于 X 分钟前」）；
4. **禁止**把 `alsoIds` 之类的派生字段当作长期真相——它必须能从 `index` 重算。
