# 需求发版管理（v2）

一个本机使用的发版流程管理工具：把飞书项目里的需求批量拉进来、自动匹配到对应分支、并盯住「有代码但没登记需求」的分支，避免发版漏项。

> v2 是新目录，v1（`..\发版小助手`）保持原样，只作对照与回退。

## 快速开始

```bash
git clone https://github.com/sunshine1130/release-pilot-v2.git   # 公开仓库，直接克隆，无需登录
cd release-pilot-v2
node server.js          # 或双击 start-server.bat
```

浏览器会自动打开。**端口被占用时会自动顺延**（并把实际端口写进 `.server-port`，页面会跟随），不需要手动改配置。

首次使用飞书项目同步前，需要登录一次（**`auth login` 不带参数**，CLI 会列出空间让你选）：

```bash
npm i -g @lark-project/meegle    # 没装过才需要
meegle auth login
meegle auth status               # 自检：authenticated 为 true 即可
```

> 别写 `--host project.feishu.cn`：各版本 CLI 对 `--host` 的支持不一致，实测有的版本会把 host 当成命令，报 `unknown command "project" for "meegle"`。若仍报 `unknown command "..."`，先 `npm i -g @lark-project/meegle@latest` 升级再试。
>
> 只有「同步飞书项目」依赖飞书；「刷新分支索引」「未登记分支」读的是你本机的 git 提交记录，没登录飞书也能用。

## 更新到最新版本

页头右上角有个**版本号徽标**（如 `v3f9a1c2`）：**点一下就检查并拉取最新代码**，拉到新版本时页面会自动刷新，
所以不需要你自己 `git pull`。

两种情况需要额外处理：

| 情况 | 现象 | 怎么办 |
|---|---|---|
| 这次更新改了 `server.js` | 提示「改动包含引擎代码」 | 关掉服务窗口、重跑 `start-server.bat`，再刷新页面（引擎在进程里，刷新页面不会重新加载它） |

仓库是公开的，拉取不需要 GitHub 登录。

也可以直接双击 `更新.bat`（等价于 `git pull --ff-only`），引擎没起来时用它。

## 分享给同事

1. 把仓库地址发给他们：`https://github.com/sunshine1130/release-pilot-v2` —— **公开仓库，不需要加协作者，也不需要 GitHub 账号**。
2. 同事克隆并启动（见「快速开始」）。之后你每次 `git push`，他们在页面点一下版本徽标（或双击 `更新.bat`）就能拉到新版。
3. 各自配置自己的环境，**这些不随仓库分享**：
   - 「项目管理」里每个项目的 **MR 地址 + 本地克隆路径**（本地路径因机器而异）；
   - 飞书项目 CLI 登录（`meegle auth login`）；
   - 需求数据本身（存在各自浏览器的 localStorage 里，可用「导出 / 导入」或项目里的 `backup/` 互相传）；
   - 卡片的折叠、待发版的排序、分组的展开收起（只存在本机浏览器，不随导出 / 备份文件走）。

## 从 v1 升级到 v2

**数据不用搬**：v2 沿用 v1 的存储键名，而浏览器存储按「协议 + 主机 + 端口」隔离，两边默认都是 `http://localhost:1949` —— 同一个源。所以关掉 v1 的服务、在 v2 目录启动，打开页面就能看到 v1 里的需求、项目清单与公用上线分支，不需要导出导入。

三个硬前提：地址要用 `localhost`（`127.0.0.1` 在浏览器眼里是另一个站，数据不通用）、端口要是 `1949`（被占用会自动顺延，等于换了一份数据）、v1 与 v2 的服务**不同时开**（都抢 1949）。

换机器 / 换浏览器 / 换目录时走导出导入：v1 点「导出」、v2 点「导入」即可。v1 的老文件只有 4 个字段，v2 兼容，且**不会清空** v2 新增的分支处置、手工关联与同步设置。

升级后要补的配置（v1 里没有）：每个项目的「本地克隆路径 + MR 地址」、飞书项目同步设置、确认「只看我的分支」。完整步骤见 [使用说明.html](使用说明.html) 第二节。

## v2 相对 v1 解决了什么

| 原来的手工动作 | 现在 |
|---|---|
| 复制需求标题、需求链接，逐条粘进表单 | **「同步飞书项目」**：按空间 + 工作项类型一次拉一批，自动填标题/链接/需求ID |
| 去各个 GitLab 仓库翻分支、逐个手选 | **分支索引**：按提交里的需求ID反查，自动挂到对应项目行（含「融合分支」） |
| —— | **未登记分支**：列出有提交却查不到需求登记的分支 |
| —— | **影响面提示**：分支行上的 `+N` 徽标，悬浮即可看到这条分支覆盖了哪几个需求（可点开飞书详情） |

## 需求区：卡片视图

需求列表已从表格改为**卡片**：一条需求一张卡片，按「新建 / 待发版 / 发版中 / 已发版」分组，
卡片左侧色条 + 一层很淡的底色标出状态（蓝 / 橙 / 紫 / 绿）。

- **卡片头**：需求名称、需求ID（点开飞书详情）、分支数摘要（如 `4 分支 · 同发 2`，一条都没挂时显示「未关联分支」），
  以及按状态给出的操作按钮（编辑 / 发版 / 标记已发版 / 恢复待发版 / 回退新建 / 删）。
- **卡片体**：按「项目 → 分支 → 影响面 → 备注」逐行排列，一条分支一行；「一同发版」的分支单独一行并带「同发」标签。
- **分支名点击** = 复制分支名 + 打开 GitLab 的「新建 MR」页，来源与目标分支已预填，
  仍要**自己在 GitLab 点提交**才会产生 MR（本工具不 push、不合并）。
- **影响面**：分支行上的 `+1` / `+3` 徽标表示这条分支的提交还覆盖几个别的需求（只覆盖 1 个是淡色、≥2 个是实心）；
  鼠标悬浮弹出气泡，写明这条分支的提交数与覆盖的需求，气泡里的需求可点开飞书详情。
- **折叠**：卡片左侧箭头折叠单条（折起后只剩一行摘要）；分组标题旁的「卡片展开 / 卡片折叠」只作用于本组；
  **已发版卡片默认折叠**；搜索时自动全部展开。
- **排序**：只有「待发版」分组有「排序」按钮 —— 进入后卡片自动折起、出现 `⠿` 拖拽手柄，拖动调整顺序，
  点「完成排序」退出，顺序自动保存；**不能跨分组拖**，要改状态请用状态按钮。
- **这些浏览状态（折叠、排序、分组开合）只存在本机浏览器**：刷新后保持，但**不跟着导出 / 备份文件走**，
  换机器或换浏览器就回到默认状态。

字段与交互细节见 [使用说明.html](使用说明.html) 第三节「需求管理」。

## 验证

```bash
node server.js                                              # 另开一个终端
cp scripts/.verify.local.example.json .verify.local.json    # 首次：按你的环境填写
node scripts/ui-verify.mjs                                  # 真实浏览器跑 114 项断言
node scripts/v1-migrate-verify.mjs                          # v1→v2 迁移路径（老数据可见/老文件可导入）7 项断言
```

脚本要驱动**本机真实环境**（本地 git 克隆、飞书空间、真实分支与需求 ID），这些属于私有数据，
所以统一放在 `.verify.local.json`（已 gitignore）——仓库里只有 `scripts/.verify.local.example.json` 模板。
缺配置时脚本会直接提示怎么建，不会跑一半失败。

覆盖：页面渲染、端口跟随、分支索引（含「远端列表优先走克隆 origin」与取不到时的降级告警）、未登记分支处置与持久化、影响面提示、飞书同步（真实调用 CLI）、按需求ID去重、导出/导入往返、备份落盘与恢复往返、版本徽标与更新检查、飞书不可用时的引导（未登录 / CLI 缺失）、引擎级安全回归（非法转义/目录穿越/跨域），以及 v1 主路径回归。

> 脚本从本机既有自动化工程的 `node_modules` 里取 Playwright，不需要往本项目装依赖。

## 前置条件与已知边界

- **需要 Git for Windows**：分支直读与反查都走本地 `git`；
- **反查需要本地克隆**：只有配了「MR 地址 + 本地路径」的项目才能算出版本覆盖的需求（没克隆就没有提交历史）；
- **未克隆的项目**仍可读分支名，但拿不到「分支覆盖了哪些需求」；
- **取远端分支名不会弹 GitLab 登录框**：优先用本地克隆自己的 `origin`（即你平时 `git fetch` 用的凭据），不拿 MR 链接去重新认证；引擎一律非交互，取不到就在界面上告警「远端分支列表未取到」——此时在对应克隆里执行一次 `git fetch` 再刷新；
- **提交信息需带需求ID**（`feat(模块-需求ID): ...`）才能被反查识别；不符合规范时系统会退回按分支名匹配，并标注来源为「分支名（推断）」；
- 索引结果有 10 分钟有效期：实测同一条分支两天内覆盖的需求就会变多。
